Step-by-step user guide

From requirements to test results

Learn how to prepare, review, export and execute your work in Auto Finance Quality.

Open Quality workspace →
01

Before you start

Auto Finance Quality turns supplied requirements into reviewed stories, scenarios and test cases. You can export the results, prepare automation files and inspect execution evidence.

  1. Sign in. Use the account supplied by your administrator. Open Quality workspace to begin.
  2. Gather your source material. Have the requirement or BRD, acceptance criteria, approved business rules and test data ready. For API tests, include the approved request contract and expected responses. For UI tests, describe the user actions and expected screen behavior.
  3. Check access. Generation needs an available model. Jira actions need a configured connection. Automation needs a configured runner and target application; ask your administrator if these are unavailable.

Keep credentials out of requirement text and uploaded documents. Use the environment configuration supplied by your administrator.

02

1. Prepare and validate requirements

  1. Enter your requirement in Finance requirement or acceptance criteria. Use the + source control to upload a document or connect a Jira ticket. Follow the file types and size limits shown by the upload control.
  2. Review the imported text. Include the relevant product, business rules, boundaries, approved data and expected outcomes. Supply missing information rather than asking the generator to invent financial rules.
  3. Review Shared business rules. Choose a test-case type: Functional, Automation (BDD / Gherkin), Non-Functional, or Both. Select the testing type and an available model.
  4. Select Validate requirements in the Business alignment gate. Address its findings against approved business sources before continuing.
  5. Select Read requirements to prepare the next stage.
A useful requirement is specific

Describe what should happen for an approved quotation request, which supplied fields may change, and the expected response for each condition. Include the actual approved limits and expected values in your source material.

03

2. Review and approve stories

  1. Select Create stories. Read each story, acceptance criterion and source excerpt.
  2. Check that the story reflects the requirement and has supporting source evidence. Correct the source or reviewable content when something is missing or incorrect.
  3. Select the stories you want to approve, enter the reviewer name or ID, and select Approve selected.
  4. Select Continue to scenarios when the required review is complete.

Upload to Jira is a separate action for approved story selections. Review the destination and selection before submitting. Approving a story does not automatically publish it.

04

3. Review and approve scenarios

  1. Select Create scenarios.
  2. Check that every scenario belongs to the correct story. Review its preconditions, action and expected outcome, including relevant positive, negative and boundary conditions.
  3. Enter the reviewer name or ID and select Approve scenarios.
  4. Select Continue to test cases.

Changing the source requirements clears downstream drafts. Finish reviewing the current source before approving the next stage. Export useful work before reloading; workflow drafts are not a substitute for saved artifacts.

05

4. Generate and review test cases

  1. Select Create test cases. The type, testing discipline and model come from the Requirements stage.
  2. Review each test case’s ID, title, objective, preconditions, data, actions and expected results. Automation cases also include Given / When / Then steps.
  3. Read the Quality Gate findings. Resolve missing information or design errors and regenerate or revise as needed.
  4. Select the cases to retain, enter the reviewer details, and use the approval controls. Review the selection again before downloading or sharing it.
Approval and execution answer different questions

A Quality Gate pass checks the test design. Reviewer approval records acceptance. A passing execution result requires running the case against its target and checking the outcome.

A title should describe the behavior being checked. For example, TC-UI-001 — Display the generation form and disable Generate until requirements are entered. Use the case ID when discussing a finding or failed run.

06

Download, preview and share

Test case documents

Use Download for Excel, CSV, PDF or JSON. Check the selected cases before export. These files describe the tests; downloading them does not execute them.

Automation files

Choose a coding language. Use View to inspect the feature file, step definitions or automation pack. Download the required artifacts after review. A feature file or bindings alone may need supporting implementation; use the complete pack and its README for execution setup.

Jira attachments

Enter the destination issue and use Attach selected to share selected cases. Check that the issue is correct and that your configured connection has permission.

Saved knowledge

Open Knowledge source to inspect retained suites and accepted outputs. Check the source and version before reusing material.

07

5. Execute and inspect results

  1. Select Continue to execution. For manual cases, perform the steps in the target application and record the outcome and actual result.
  2. For automation, arrange for the reviewed pack to be installed in the configured project and its target URL, credentials and input data to be configured. Follow the pack’s README or ask the automation owner.
  3. Select Refresh execution plan. Read the readiness message and feature list. Confirm the listed scenarios are the ones you intend to execute.
  4. When ready, select Run feature files. Individual results appear after the runner returns. Read failed-case details and Runner output.

Languages and script types have their own execution setup. Downloading a Java, Python, JavaScript, TypeScript, Ruby, performance or database pack does not make it executable by the configured C# ReqnRoll runner.

Check the scope of the run

Progress & execution → Run BDD tests runs the configured repository project. A repository smoke-test pass does not prove that your newly generated suite ran. Confirm the execution plan, discovered cases and actual results.

08

Find reports and track progress

  • Project dashboard: inspect the workspace overview and suite activity. Read its reporting-scope note before treating totals as a delivery or release decision.
  • Progress & execution: refresh history, select a run and inspect its status, case results and execution logs. Export history as CSV or download the Allure HTML report when available.
  • Quality Lifecycle: inspect suite traceability and Application usage. Usage totals describe recorded activity; they are not a count of unique approved cases.
  • Runtime logs: inspect application events and reference IDs when investigating an operation.

Passed, failed and not-run counts describe execution evidence. A build error, authentication error or timeout can prevent a usable result. An Allure report-generation error is reported separately and does not turn failed tests into passed tests.

09

Troubleshooting

A button is disabled

Read the message beside the current stage. Check requirements validation, the selected cases, reviewer details and approval of the preceding stage. Execution also requires a ready plan and target configuration.

No model is available

Refresh the model list. If it remains unavailable, ask the administrator to verify provider access and configuration. Capture the displayed error or reference ID.

Generation stops or fails

Inspect the activity feed and Runtime logs. Resolve missing source details or provider errors before retrying. Avoid starting repeated requests while the current operation is still active.

A test run fails

Open the run’s case results and Technical Logs or Runner output. An assertion failure identifies an actual/expected mismatch; a startup or build error means the runner may not have executed the cases. Record the failed case ID and the exact message.

The hosted run times out

Refresh run history before retrying to check whether the run completed. Share the run ID, time, error and runner output with the administrator. Ask them to check the deployed build, target configuration and execution limits.

Report or Jira action fails

For a missing report, read the report-generation error separately from test outcomes. For Jira, check the selected records, destination and reviewer approval; ask the administrator to verify connection permissions.

When reporting an issue, include the page, action, run or case ID, time, expected behavior and displayed error. Remove passwords, tokens and confidential test data.

10

Quick reference

Requirement
The supplied business need or rule.
Story
A reviewable unit of work linked to source requirements.
Scenario
A condition or journey with a defined expected outcome.
Test case / suite
An executable or manual check / a collection of checks.
BDD / Gherkin
Given describes setup, When describes an action, and Then describes the expected result.
Automation pack
Feature files and supporting code, configuration and input data used to run automated checks.
